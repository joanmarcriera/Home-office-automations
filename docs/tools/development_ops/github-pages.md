# GitHub Pages

## What it is
GitHub Pages is GitHub's static site hosting service for project sites, documentation, blogs, and other repo-backed web content. It integrates directly with GitHub repositories to automate the deployment of static files. As of June 2026, it is the standard for hosting AI-generated documentation and project microsites.

## What problem it solves
It gives teams the simplest path from a Git repository to a publicly hosted static website. It removes the need for managing separate hosting infrastructure for static content and provides:
- **Automation**: Direct integration with GitHub Actions for seamless CI/CD.
- **Security**: Automatic SSL via Let's Encrypt and enforced HTTPS.
- **Cost Efficiency**: Free hosting for public repositories, making it ideal for open-source and personal projects.

## Where it fits in the stack
**Development & Ops / Repo-Native Static Website Hosting**. It is the preferred choice when the site should stay tightly coupled to a repository, such as for documentation generated by [Claude Code](claude-code.md) or [Aider](aider.md).

## Typical use cases
- Project documentation sites (e.g., MkDocs, Docusaurus).
- Public blogs and portfolios.
- Tool directories generated from repository data.
- Landing pages for AI agents and MCP servers.
- Automated deployment of [Playwright](playwright.md) test reports.

## Strengths
- **Zero Configuration**: Many sites can be deployed with just a few clicks or a standard YAML file.
- **Scalability**: Backed by GitHub's global CDN for fast content delivery.
- **Integration**: Works natively with Jekyll and supports custom builds via GitHub Actions.
- **Transparency**: The site source is visible in the repository (for public repos), promoting collaboration.

## Limitations
- **Static Only**: No server-side logic (PHP, Node.js, etc.) is supported.
- **Usage Limits**: Soft limits on bandwidth (100GB/month) and repository size (1GB).
- **Public by Default**: On free tiers, pages are always public if the repository is public.

## When to use it
- When the website is primarily documentation or static content.
- When you want to minimize maintenance and infrastructure overhead.
- When the repository is already the source of truth for the site.
- When using [MkDocs](../../mkdocs.yml) for repository-wide knowledge bases.

## When not to use it
- When the site requires a database, authentication, or dynamic backend.
- When [Vercel](vercel.md) or [Cloudflare Pages](cloudflare-pages.md) is required for advanced edge functions or Next.js support.
- When strict IP-based access control or complex request routing is needed.

## Getting started
To enable GitHub Pages for your repository:
1. Navigate to **Settings** > **Pages** in your GitHub repository.
2. Select the source (e.g., **GitHub Actions** or a specific branch).
3. If using Actions, select a template (like "Static HTML") to generate a deployment workflow.

## CLI examples
You can manage and monitor GitHub Pages deployments using the GitHub CLI (`gh`).

```bash
# Check the status of the latest Pages deployment
gh run list --workflow "Deploy to GitHub Pages"

# List the environments for the repository
gh api repos/:owner/:repo/environments

# Trigger a manual deployment (if workflow_dispatch is enabled)
gh workflow run "Deploy to GitHub Pages"
```

## API examples
The GitHub REST API provides endpoints to manage Pages configuration and deployment.

### GET /repos/{owner}/{repo}/pages
Retrieve the configuration and build status of a GitHub Pages site.

```bash
curl -L \
  -H "Accept: application/vnd.github+json" \
  -H "Authorization: Bearer <YOUR-TOKEN>" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  https://api.github.com/repos/OWNER/REPO/pages
```
