# gVisor

## What it is
gVisor is an open-source security application kernel created by Google that provides strong sandbox container isolation. Written in Go, gVisor intercepts Linux system calls made by containerized applications and implements a lightweight kernel in user space (`Sentry`) paired with a file access proxy (`Gofer`). By restricting containerized processes from interacting directly with the host Linux kernel, gVisor eliminates traditional container breakout vulnerabilities. In 2027, gVisor serves as a critical runtime engine powering multi-tenant AI code execution environments, untrusted agent tool sandboxes, and secure container runtimes (`runsc`).

```
+-----------------------------------------------------------------------------------+
|                            GVISOR RUNSC CONTAINER SANDBOX                         |
+-----------------------------------------------------------------------------------+
|                                                                                   |
|  +---------------------+       +-----------------------+      +-----------------+ |
|  | Untrusted Agent     | ----> | gVisor Sentry Kernel  | ---> | Gofer File      | |
|  | Code Execution Proc |       | User-Space Syscall Engine    | Proxy           | |
|  +---------------------+       +-----------------------+      +-----------------+ |
|                                                                        |          |
|                                                                        v          |
|  +---------------------+       +-----------------------+      +-----------------+ |
|  | FastMCP 3.1 Gateway | <---- | Restricted Host Linux | <--- | Filtered Host   | |
|  | Execution Result    |       | Kernel Interface      |      | System Calls    | |
|  +---------------------+       +-----------------------+      +-----------------+ |
+-----------------------------------------------------------------------------------+
```

## What problem it solves
Executing dynamic code generated by autonomous AI agents (such as Python scripts, bash commands, or WASM binaries) directly within standard Linux containers (Docker / runc) poses severe security risks. Standard Linux containers share the host kernel surface; an exploited kernel vulnerability or privilege escalation bug allows malicious code to escape into the host environment or access private network sockets. gVisor solves this by placing a user-space kernel between the containerized application and the host OS, drastically reducing the accessible host attack surface.

## Where it fits in the stack
**Infrastructure / Container Sandboxing & Security Runtime**. gVisor sits at the container engine runtime layer as OCI runtime plugin `runsc`, operating underneath orchestrators like [Docker](docker.md), [Docker Sandbox for AI Agents](docker-sandbox-ai-agent.md), or [Kubernetes (K3s)](k3s.md).

## Typical use cases
- **Untrusted Agent Code Interpreter Execution**: Safely executing agent-generated Python scripts, shell commands, or network scrapers in isolated sandboxes.
- **Multi-Tenant Microservices Isolation**: Isolating customer-facing agent workloads on shared Kubernetes clusters without risking host kernel compromised state.
- **Secure File Processing**: Processing untrusted PDF uploads, images, or archive extractions within strict sandbox perimeters.
- **Zero-Trust Tool Isolation**: Wrapping FastMCP tool execution containers in gVisor to prevent lateral network movements or privilege escalation.

## Strengths
- **Defense in Depth**: User-space kernel (`Sentry`) implements Linux syscalls, preventing containerized applications from issuing direct host kernel syscalls.
- **Seamless Docker & Kubernetes Integration**: Drop-in replacement for `runc` as OCI-compliant runtime `runsc`.
- **Low Memory Overhead**: Starts in milliseconds with lightweight memory consumption compared to full hardware virtual machines (KVM/Firecracker).
- **Fine-Grained System Call Interception**: Configurable security profiles allowing strict file and socket isolation rules.

## Limitations
- **Syscall Emulation Performance Penalty**: High-frequency system call workloads (e.g., intensive file IO or raw network sockets) incur higher CPU overhead compared to native `runc`.
- **Incomplete Linux Syscall Surface**: Rare or highly specialized Linux syscalls may not be fully implemented in the user-space kernel.

## When to use it
- When running untrusted, model-generated code or execution scripts within AI agent workflows.
- When multi-tenant isolation is required without the heavy resource overhead of full hardware virtual machines.
- When enforcing zero-trust security postures across Docker and K3s container clusters.

## When not to use it
- When running trusted, latency-critical compute tasks requiring direct GPU hardware access or raw I/O throughput (use standard `runc` or Podman).
- When full hardware virtualization with dedicated kernel instances is required for regulatory compliance (use Firecracker or Kata Containers).

## Architecture & Technical Deep Dive

gVisor's architecture relies on two core processes: the `Sentry` and the `Gofer`:

```
                           GVISOR ARCHITECTURE PIPELINE

    Container Process (Untrusted Code)
                    │
                    ▼
     ┌──────────────────────────────┐
     │ Syscall Interception (KVM/systrap)
     └──────────────┬───────────────┘
                    │
                    ▼
     ┌──────────────────────────────┐
     │        Sentry Kernel         │  <--- Implements Linux Kernel Syscalls
     │     (Go User-Space Engine)   │       in Safe User Space
     └──────────────┬───────────────┘
                    │
                    ▼
     ┌──────────────────────────────┐
     │         Gofer Process        │  <--- Isolated File Access Proxy
     │     (Host File Systems)      │       Communicates via 9P Protocol
     └──────────────┬───────────────┘
                    │
                    ▼
            Host Linux Kernel
```

1. **Sentry**: Acts as the user-space kernel process that emulates Linux system calls (such as `sys_read`, `sys_write`, `sys_mmap`), isolating application logic from the host kernel.
2. **Gofer**: Runs as an isolated file system proxy process outside the sandbox, handling file access requests on behalf of the Sentry using the 9P protocol.
3. **Platforms (systrap / KVM)**: Uses CPU virtualization extensions (KVM) or ptrace-like traps (`systrap`) to intercept syscalls from application code into the Sentry.

## Getting started

Install `runsc` and configure Docker to use gVisor runtime:

```bash
# Download and install runsc binary
curl -fsSL https://storage.googleapis.com/gvisor/releases/release/latest/x86_64/runsc -o /usr/local/bin/runsc
chmod +x /usr/local/bin/runsc

# Configure Docker daemon to register gVisor runtime
runsc install

# Restart Docker daemon
systemctl restart docker
```

```bash
# Run container using gVisor (runsc) runtime
docker run --runtime=runsc --rm -it alpine uname -a
```

## CLI examples

```bash
# Execute untrusted Python script in a gVisor sandboxed container
docker run --runtime=runsc --read-only --network none --rm -v $(pwd):/workspace python:3.11-slim python /workspace/agent_code.py

# Verify gVisor sandbox runtime status inside container
docker run --runtime=runsc --rm alpine dmesg | grep -i "gvisor"

# Start container with debug logging enabled for runsc
runsc --debug --log=/tmp/runsc.log run my-sandbox-container
```

## API examples

### FastMCP 3.1 Controller & Pydantic v2 Sandbox Execution Gateway
The following Python module demonstrates managing gVisor container sandboxes using a **FastMCP 3.1** server with strict **Pydantic v2** schema validation.

```python
import os
import logging
from typing import Optional, List
from pydantic import BaseModel, ConfigDict, Field, field_validator, ValidationError
from fastmcp import FastMCP, Context

# Configure logging
logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("gVisor-Controller")

# Initialize FastMCP 3.1 Server
mcp = FastMCP("gvisor-sandbox-service")

# Pydantic v2 Sandbox Execution Request Model
class SandboxExecutionRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")

    code_script: str = Field(..., min_length=1, max_length=50000, description="Python or Shell script to execute in sandbox")
    language: str = Field(default="python", description="Target execution runtime language")
    timeout_seconds: int = Field(default=30, ge=1, le=300, description="Execution timeout limit in seconds")
    network_enabled: bool = Field(default=False, description="Whether outbound network access is granted")

    @field_validator("language")
    @classmethod
    def validate_language(cls, v: str) -> str:
        allowed = {"python", "bash", "javascript"}
        lang = v.strip().lower()
        if lang not in allowed:
            raise ValueError(f"Language '{v}' not supported. Allowed: {allowed}")
        return lang

@mcp.tool()
async def execute_in_gvisor_sandbox(
    request_dict: dict,
    ctx: Optional[Context] = None
) -> dict:
    """
    Executes untrusted agent script inside gVisor (runsc) sandboxed container environment.

    Args:
        request_dict: Dictionary matching SandboxExecutionRequest model.
        ctx: FastMCP Context.
    """
    if ctx:
        await ctx.info("Validating sandbox execution request with Pydantic v2...")

    try:
        req = SandboxExecutionRequest.model_validate(request_dict)
        if ctx:
            await ctx.info(f"Executing {req.language} script in gVisor (network={req.network_enabled})...")

        # Simulated sandbox execution output
        return {
            "status": "completed",
            "runtime": "runsc (gVisor)",
            "exit_code": 0,
            "stdout": "Sandbox execution finished cleanly.",
            "stderr": "",
            "execution_time_ms": 240,
            "network_enabled": req.network_enabled
        }
    except ValidationError as ve:
        logger.error(f"Validation failure: {ve}")
        raise ValueError(f"Invalid execution request: {ve}")

@mcp.tool()
async def get_gvisor_status(ctx: Optional[Context] = None) -> dict:
    """Queries current gVisor runsc runtime configuration and system platform."""
    return {
        "engine": "gVisor (runsc)",
        "sentry_version": "20261005.0",
        "platform": "KVM / systrap",
        "docker_runtime_registered": True
    }

if __name__ == "__main__":
    mcp.run()
```

## Integration patterns
- **Sandboxed Execution Pattern**: Wrap agent code interpreter modules in gVisor containers as detailed in [Sandboxed Code Execution](../../knowledge_base/patterns/sandboxed-execution.md).
- **Docker Sandbox Integration**: Leverage gVisor as the security runtime underlying [Docker Sandbox for AI Agents](docker-sandbox-ai-agent.md).

## Best practices & Security
- **Read-Only Root Filesystems**: Mount container root filesystems as read-only (`--read-only`) inside gVisor containers, writing temporary files to ephemeral `tmpfs`.
- **Disable Network Access**: Default to `--network none` when running agent code interpreters unless explicit outbound API access is required.
